# Phase 1-5 로컬 결과

2026-11-10, Intel Core i5-14500의 Ubuntu 24.04 WSL2와 Docker Desktop에서 측정했다.
Docker 엔진은 논리 CPU 20개와 15.50 GiB 메모리를 인식했다. 엔진 27.5.1, Compose 2.32.4,
k6 0.57.0을 사용했고 컨테이너별 CPU·메모리 제한은 설정하지 않았다.
[환경 기록](environment.json)

각 조건은 12초씩 한 차례 실행했다. 활성 브랜드당 VU 상한은 4, 주문 목표 비중은 35%였다.
Idle은 대기 VU 1개로 측정 창을 유지했다. 각 조건 전 브랜드별 읽기 요청을 한 차례 실행했다.
부하 조건, 전체 k6 원시 포인트, 주문별 시간과 4초 간격 목표의 시스템 표본은 각 하위 디렉터리에 있다.
지표 정의와 수집 한계는 [실험 실행 문서](../../README.md)에 정리했다.

## 컨테이너 자원

스냅샷에서 본 Docker CPU%와 메모리 MiB의 개별 최고치다. CPU%는 Docker가 보고한 값이며 호스트 20개 논리 CPU로 나누지 않았다. 부하 종료 후 처리 구간 표본을 포함한다.

| 시나리오 | Catalog | Order | Worker | PostgreSQL |
| --- | ---: | ---: | ---: | ---: |
| Idle | 1.70% / 220 MiB | 2.34% / 246 MiB | 1.67% / 236 MiB | 1.05% / 63 MiB |
| Normal | 5.57% / 223 MiB | 10.23% / 256 MiB | 6.06% / 243 MiB | 1.66% / 66 MiB |
| A 집중 | 24.72% / 228 MiB | 16.47% / 262 MiB | 12.12% / 249 MiB | 3.18% / 72 MiB |

Idle의 Order와 Worker에는 헬스체크 및 백그라운드 Publisher·SQS 폴링 비용이 포함된다.
컨테이너별 표본이므로 프로세스 내 작업별 자원을 분리할 수 없다.

## A 집중 부하에서 Worker 비교

| POS 지연 / Worker 수 | A 완료 p95 (s) | A SQS age p95 (s) | A 부하 창 처리량 (주문/s) | A Outbox pending / SQS visible 최고치 | 부하 종료→확인 완료 (s) |
| --- | ---: | ---: | ---: | ---: | ---: |
| [0ms / 1](single-spike/summary.json) | 65.63 | 56.39 | 0.903 | 18 / 25 | 70.9 |
| [0ms / 2](single-spike-workers-2/summary.json) | 28.67 | 19.22 | 1.217 | 18 / 17 | 31.0 |
| [400ms / 1](single-spike-pos-400ms/summary.json) | 88.85 | 79.00 | 0.607 | 18 / 30 | 95.0 |
| [400ms / 2](single-spike-pos-400ms-workers-2/summary.json) | 42.08 | 32.05 | 0.761 | 18 / 24 | 47.0 |

- **발행과 소비 양쪽에서 적체를 관측했다.** A 주문 유입은 43건/12초였다. Publisher는 브랜드별
  한 이벤트를 처리한 뒤 500ms의 스케줄 간격을 두므로 이 유입을 따라가기 어렵다. Worker는 한 스레드에서
  브랜드별 큐를 순회하며 빈 큐에서 최대 1초씩 대기한다. 낮은 CPU 표본과 Worker 증설 효과를
  함께 보면 순차 소비와 대기가 병목 후보에 해당한다. 큐별 폴링 시간을 직접 계측해야 각각의 비중을 분리할 수 있다.
- **POS 지연 동안 DB 트랜잭션 점유를 관측했다.** Worker 1개·400ms 조건에서 PostgreSQL 세션이
  `idle in transaction`인 표본과 최대 401ms의 트랜잭션 나이를 관측했다. A 수신→ACK p95는
  20ms에서 423ms로 늘었다. 관측 표본에 PostgreSQL Lock 대기 세션은 없었고, 1개 Worker 조건에서
  브랜드당 세션 최고치는 2개였다. 이 실험에서 Hikari 연결 풀 포화는 확인하지 못했다.
- **B/C의 비동기 처리에도 영향이 있었다.** Worker 1개에서 B/C 완료 p95는 POS 지연 추가 전
  0.67/0.39초, 추가 후 2.59/2.17초였다. Worker 2개·400ms 조건에서는 1.46/0.95초였다.
  브랜드당 완료 표본은 9건이므로 변화 방향을 보여주는 탐색 결과로 해석한다.

후속 실험에서는 브랜드별 제한된 병렬 폴링 또는 배치를 우선 비교하고, Outbox 배치 크기와 발행 간격은
별도로 변경해 효과를 분리한다. POS 호출 중 열린 트랜잭션을 줄이는 설계는 장애 재처리와 멱등성
조건을 유지한 상태에서 비교한다. 이번 Phase에서는 Worker의 잠금·전달 구조를 유지했다.

## 회귀 및 로컬 이미지 검증

Gradle 전체 빌드가 성공했다. 변경 전 통합 테스트 18건이 통과했다. 변경 후 첫 재실행에서
Source 단일 브랜드 테스트가 Docker의 동적 포트 매핑이 게시되기 전에 빈 값을 파싱했다.
포트 게시와 readiness를 함께 기다리도록 테스트를 수정한 뒤 전체 18건이 다시 통과했다.

네 이미지를 빌드해 UID 10001, 이미지 기본 readiness, 별도 liveness, 런타임 포트 및 SIGTERM
정상 종료를 확인했다. 이미지 환경·히스토리·애플리케이션 JAR 검사에서 로컬 실험용 비밀번호와 키가
발견되지 않았다. Target에서 사용한 이미지 ID를 그대로 Source에 사용했다. A 자격 증명·큐만
주입한 Source에서 B/C JWT는 거부됐고, POS가 수락한 직후 Worker에 SIGTERM을 보내도 A 주문은
완료됐으며 큐는 비워졌다. [이미지 검증 원시 결과](ecs-local.json)

## 배포 전 재검증

로컬 실험은 조건당 1회, 12초의 탐색 측정이다. p99와 4초 간격 자원·세션 표본은 순간 피크에 민감하다.
AWS에서는 동일 부하를 각 조건에서 3회 이상 반복하고 RDS TLS·연결 수·잠금, 실제 SQS long poll·가시성·DLQ,
ECS Task Role, 외부 JWKS, ALB 드레이닝 및 Task CPU·메모리 한도를 검증한다. AWS에서 얻는 성능·비용 데이터는
이 로컬 자료와 별도로 저장한다.
